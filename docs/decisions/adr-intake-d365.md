# ADR: World Enterprise forms backend on the org Function + Logic App + D365 pattern

Issue: WorldEnterpriseGroup/worldenterprise#118 (milestone "Forms backend: Azure Functions + Logic Apps + D365"; follow-ons #119 provision, #120 lead write + notification, #121 e2e, #122 release wiring)
Status: accepted. Date: 2026-10-28. Decided under the CEO directive of 2026-10-28: no third-party form relays; every site form goes to the WE intake Azure Function, which writes to Dynamics 365 and triggers an Azure Logic App that notifies info@worldenterprise.org. Infrastructure is code in Git and nothing is hand-built.

The evidence below was gathered read-only (sibling repositories, the GitLab API, the Azure CLI, Dataverse Web API GET requests, a Cloudflare zone lookup). No secret value was read or recorded; only secret names appear in this document.

## Decision in one paragraph

Keep `infra/intake` as the Function (it is already a near-clone of the Global Enterprise and HardMagic brief-delivery Functions). Deploy it into the MPN subscription next to those siblings, behind the shared `taodoor-standard` Front Door, writing to the shared **Dream Dataverse** environment `https://dream.crm.dynamics.com` inside a new "World Enterprise" business unit. Add two things the Function lacks: (1) a standard D365 **Lead** write (the house pattern for contact-style intake, as Trustora does), and (2) a **Logic App** (`logic-we-intake-notify`, Consumption, defined in Bicep from a JSON definition in git) that the Function calls after the durable write and that emails info@worldenterprise.org. ACS stays, for visitor-facing brief and confirmation mail only. The deploy identity is an Entra app with a **client secret**, not GitLab OIDC federation, because Entra cannot reach our GitLab issuer (it is reachable only on the internal overlay network). Nearly every blocker in the runbook can be done with credentials we already hold (details in section d).

## (b) Gap between `infra/intake` and the pattern, and exactly what to change

`infra/intake` already matches variant 2: Node 24 Flex Consumption, UAI, storage with shared-key off, ACS Email, Key Vault references, Front-Door-only ingress, idempotent Dataverse writes, what-if gate. Gaps:

1. **Deploy identity (wrong mechanism).** `docs/intake-runbook.md` OP-AZURE and `ci.yml` (`.intake-azure`, `id_tokens`, `az login --federated-token`) assume GitLab OIDC federation. Our own Terraform says it cannot work: `focushive-privileged/form_intake_deploy_ci.tf`, `logicapps_estate_ci.tf` and `gator-teams/main.tf` all state "GitLab OIDC cannot federate to Entra (the issuer is overlay-only)". The internal GitLab host resolves to an address on the overlay network that Entra cannot reach. HardMagic carries a federated credential on its app, but its pipeline actually logs in with a client secret (`AZURE_CLIENT_SECRET` CI variable, AKV `hardmagic-gitlab-azure-client-secret`). Change: make `.intake-azure` log in with `INTAKE_AZURE_CLIENT_SECRET` (copy HardMagic `.gitlab/ci/brief-delivery.yml` `.azure_oidc` shape), drop `id_tokens`, update OP-AZURE.
2. **D365 mapping (missing Lead).** Today: Contact + Account + custom `we_engagement` row (`dataverse/definition.json`, `src/azure/dataverse.ts`, `src/logic/mapping.ts`). Nothing writes `lead`, and the role has no Lead privileges. Change:
   - Keep `we_engagement` as the per-submission ledger and idempotency anchor (alternate keys `we_engagement_requestid`, `we_engagement_tokenhash`; it holds delivery status, consent timestamps, suppression, nurture state, which a Lead cannot hold). GE and HardMagic keep the same ledger beside native Contact/Lead.
   - Add a **Lead** create for `apply`, `contact`, `investor-interest`, `partner-enquiry`, and `brief-request`: `subject = "World Enterprise <form> - <requestId>"` (deterministic; replay resolves the existing Lead, per Trustora, so no schema change to the shared lead table), `firstname/lastname` split from `name`, `emailaddress1`, `companyname`, `websiteurl` (companyUrl), `leadsourcecode` Web, `description` = labelled lines of the remaining fields (stage, audience, briefId, topic, seats, partnerCategory, investorKind, focus, offer, message, page, consent time). `lead.description` MaxLength is 100000 in Dream, so the USIVA 2000-char problem does not apply. `ownerid@odata.bind` = the World Enterprise owner team; never owner from the browser. Store the lead id in the engagement row (add `we_leadid` lookup in `definition.json`).
   - `newsletter` stays Contact + engagement only (no sales Lead, consistent with consented-list handling in `docs/forms-privacy-facts.md`); an existing Contact match is reused (current ambiguity handling `we_review=contact-ambiguous` stays).
   - Order stays: engagement row (durable) then Lead then 202; a Lead failure after the engagement row is retried by the existing sweep and never fails the visitor (the ledger row is the system of record).
   - `definition.json` role privileges: add `Lead` Create, Read, Write, Append, AppendTo (Local depth), plus Local Read on `prvReadAsyncOperation` (Trustora found Dataverse needs it during Lead creation). No Delete, no Global depth.
3. **info@ notification (missing; the CEO's Logic App).** The Function only has ACS visitor mail and an optional signed webhook. Change:
   - Add `infra/intake/iac/notify.bicep` (called from `intake.bicep`): `Microsoft.Logic/workflows` `logic-we-intake-notify-<suffix>`, Consumption, region eastus, `definition: loadJsonContent('../logicapps/we-intake-notify.definition.json')`, definition kept in git (the mtcottages and emmy convention, but deployed by the same Bicep so there is no separate manual `az logic workflow update`). `accessControl.triggers.openAuthenticationPolicies` allows only the Function's UAI (issuer tenant `2febe90d-...`, audience `https://management.core.windows.net/`, oid of `uai-we-intake-*`), exactly as `form-intake-proxy/scripts/logicapp-access.sh` does; no `sig` is stored or needed.
   - Function side: a new `Notifier` port in `src/service/ports.ts` and adapter in `src/azure/` that POSTs `{requestId, form, audience, name, email, company, topic, summary, leadId}` with the UAI token and header `x-ms-client-tracking-id: <requestId>` (so a run can be found by request id). The call happens after the durable write; failure never fails the request (same rule as a failed visitor email: mark the row and let the retry sweep re-send; the Logic App dedupes on requestId via the tracking id). App setting `NOTIFY_LOGICAPP_URL` is the trigger URL without `sig` (not a secret in OAuth-only mode). This replaces `WEBHOOK_URL`/`worldenterprise-intake-hmac-secret`; retire that webhook path rather than keep two mechanisms.
   - Logic App actions: Request trigger (schema), `Send an email` to `info@worldenterprise.org` with subject `[WE <form>] <name>`, body = the summary and a link to the Lead, no raw `message` beyond what the notice allows, then a Response 202.
   - **Which connection sends the mail (reuse question).** Existing Logic Apps use user-delegated `office365` connections: `office365-3` (TLI-Analytics-Group, connected as a named staff member) and `office365` (tli_interest, status Error, bound to a named staff member). Do **not** reuse them: mail would be sent as a named person's mailbox, the tokens are interactive, and one is already broken. A new Office 365 connection needs an interactive OAuth consent (a human click) and is bound to one person. Recommendation: the Logic App calls the **ACS Email REST API with its own system-assigned managed identity** (HTTP action, role "Communication and Email Service Owner" granted in Bicep like the Function's), sender `DoNotReply@<managed domain>`, recipient `info@worldenterprise.org`. No consent, no secret, no connection resource, fully code. Risk: the ACS managed-domain sender may be spam-filtered by Exchange; mitigate with a mail-flow allow rule for that sender in the tenant (one-time human/Exchange admin step, optional) or move to a verified `mail.worldenterprise.org` sender (DNS is in Terraform, see c). Fallback if the CEO insists on Outlook-sent mail: add an `office365` connection in Bicep and have an operator authorize it once.
   - The `dynamicscrmonline` connection in `tli_interest` (connected as a named staff member) could be reused to let the Logic App create the Lead (variant 1 as `mtcottages-intake.definition.json` does). We do not, because that makes a single user's delegated token the write path and loses the Function's idempotency and 503-on-failure contract. It remains the documented fallback.
4. **ACS stays.** Brief-link, confirmation and (later) nurture mail to visitors continues through ACS Email, as in GE, HardMagic and Taomgt (privacy facts already state ACS, tracking off). Logic App office365 sending is the wrong tool for visitor mail (a person's mailbox, per-connection throttling, no unsubscribe/suppression integration). Sender: start on the Azure-managed domain (OP-MAIL default), move to a verified `mail.worldenterprise.org` domain later via Bicep + Cloudflare Terraform.
5. **Resource group and scope.** `main.bicep` is subscription-scoped and creates `rg-worldenterprise-intake`. Because the CI identity can only be given narrow rights by our privileged Terraform (see c), either grant it the subscription rights Bicep needs or (preferred, mirrors `HardMagic BriefLock Deployment Operator` at sub plus RG roles) have `focushive-privileged` Terraform create the RG, and the deploy SP's `Contributor` + condition-limited `Role Based Access Control Administrator` there, and keep `main.bicep` as is.
6. **Front Door / DNS.** MR !726 is the right shape; it just needs the Front Door id the runbook already expects (`9640fdb7-bfd5-4890-a984-5a5a7217ad3d`, no longer an unknown).
7. **Docs.** `docs/intake-runbook.md` (OP-AZURE federated text, OP-DV "cannot be code", OP-FD), `docs/forms-privacy-facts.md` (add: each submission also becomes a Lead, and an internal email goes to info@) and the privacy page change in the same MR (repo rule: notice and facts change together, and the wp-10 pin).

## (d) Blockers: human versus "we can do it"

**The operator can do all of this with credentials the organization already holds** (the operator account is Owner on the MPN subscription, User Access Administrator at `/`, and holds the **System Administrator** role in Dream, verified by WhoAmI and a role query):
- Create the deploy app, secret and role assignments (needs Owner/UAA on MPN: held; `focushive-privileged` README says role assignments there need this and not the Atlantis runner, so the Terraform MR is applied by the operator login, the same way as `sp-form-intake-deploy`, whose app and role were created with `az` and adopted via `imports.tf`).
- Create the three Key Vault secrets (`az keyvault secret set`, vault is in the same subscription, we can list it; generating the random unsubscribe key needs no human).
- OP-DV (register the Function UAI and the deploy SP as Dataverse application users, create BU/team/role/table): the runbook says "this is the one step that cannot be code". It can: our Dream System Administrator login creates the application user for the deploy SP with a Web API POST on `systemusers` (applicationid), then `intake:dataverse` runs under that SP. Recommendation: grant the CI SP System Administrator in Dream only for the first apply, then reduce or remove it.
- OP-FD: merge MR !726 (it is a draft only because the operator was not ready) and the Terraform for DNS in `dns-intake` (the zone is in the TaoMgt Cloudflare account we manage).
- OP-AZURE: no external dependency. The Logic App, Communication Services, storage and Function providers are all Registered in the subscription.

**Genuinely needs a human decision or action:**
1. **Approval to touch shared D365 and shared infrastructure** (a new BU, role and application users in the production Dream org; MR to the shared Front Door repo; the CI SP holding Dataverse System Administrator temporarily). These are technically ours to do, but the global rules reserve business-impacting actions to the CEO; recommend a single yes on this ADR.
2. **OP-RETAIN and OP-COUNSEL** (retention wording, counsel review, `NURTURE_ENABLED`): unchanged, do not block forms going live because nurture stays off.
3. **Spam-filter allow rule** for the ACS managed-domain sender to info@ (Exchange admin task) or the decision to verify `mail.worldenterprise.org` as the sender; only if the first test mail lands in junk. We can add the DNS records in Terraform, but the tenant mail-flow rule is an Exchange admin console action unless it is added through the `m365-config` Terraform environment (check there first).
4. **Interactive Office 365 OAuth consent**, only if the CEO rejects the recommended ACS-from-Logic-App design and wants Outlook-sent mail. That one click cannot be code.
5. Mailbox naming: `site.ts` still marks `hello@` and `apply@` unconfirmed; confirm which public addresses the site shows (not a blocker for the backend).

## (e) E2E proof that a submission landed in D365

Follow `form-intake-proxy/scripts/e2e.sh` and Trustora's UUID-scoped smoke, adapted to the repo's existing Playwright-in-K8s model (#121):

1. **Submit** through the real public path `https://intake.worldenterprise.org/api/intake` (Front Door, WAF, Function), using the site's real form where possible (`tests/e2e/forms.spec.ts` pattern) with a fresh `requestId` and a synthetic address `e2e-<requestId>@e2e.invalid` (RFC 2606 reserved, so no real mail can go anywhere; use `contact` and `apply`, which send no visitor email; `brief-request` would try ACS to that address and is skipped or run only against a mailbox we own). The Function's 5 per hour per address and per email limit is respected by using one submission per form per run.
2. **Read back identity.** A dedicated Entra app `sp-worldenterprise-intake-e2e` (secret in AKV `worldenterprise-intake-e2e-sp-secret`, exposed to the K8s test pod through the existing ExternalSecret path like the other e2e secrets, never the runtime UAI), registered as a Dataverse application user in the World Enterprise BU with a small role: Local Read and Delete on `Lead`, `Contact`, `we_engagement` only, no Write, no Create. Created by `definition.json` (a second role and application user in the same idempotent applier). It also has "Logic App Operator" on the notify workflow to read run history.
3. **Assert**: query `we_engagements?$filter=we_requestid eq '<id>'` (alternate key) and expect one row with `we_status` received or delivered and the lead lookup populated; query `leads?$filter=subject eq 'World Enterprise <form> - <id>'` and check owner team = World Enterprise Intake, `emailaddress1`, `leadsourcecode`, and description lines; replay the same POST and assert still exactly one Lead and one row (idempotency); assert the Logic App run with client tracking id = requestId is `Succeeded`; for the mail, the Logic App treats `*@e2e.invalid` submissions as test traffic and sends to a test mailbox/subject prefix `[TEST]` (documented in the definition and covered by a unit test of the definition JSON) so info@ is not spammed.
4. **Cleanup** in a `finally` (so a failed assertion still cleans up): delete the Lead(s) by id, delete the `we_engagement` row by alternate key, delete the Contact only if its email is the synthetic address and no other rows reference it (never delete a Contact matched by a real address; HardMagic's operations doc states the same rule), then re-query and assert zero rows. A nightly sweeper in the same job deletes anything with `e2e.invalid` older than a day, so a crashed run cannot leave debris. Dataverse auditing on the table keeps the record that the test ran.
5. **Not used**: the runtime managed identity (it has no Delete and should not gain it for tests, unlike Trustora, whose role carries Delete for its smoke; ours stays least-privilege), a protected smoke route in production code, or any manual portal check.
