## Decisions

- **The trigger is in the utility bar, not in the header row.** `menu.spec` requires the nav row to fit at 1100 to 1279 px with the nav ending 8 px before Apply, so nothing can be added to that row. The utility bar already carries a Search link. Without JavaScript it stays a link to `/search/`. `palette.ts` reads the command list and then hides the link (`[data-palette-fallback]`) and shows a button with the same label (`[data-palette-open]`), so the swap moves nothing. The drawer has the same pair, at 3rem.
- **Commands are built at build time** from `resolveNav`, `resolveUtility`, `resolveFooter` and the route state (`buildPaletteCommands`), serialized once into `data-commands`. `isLive` is checked again in the builder. Sections and direct items come first, so a page that is both (Pricing) is listed under its own name and a search for "pricing" finds it. The island parses with `JSON.parse` in a `try`; a bad item is dropped and reported once.
- **Pagefind** is loaded like `we-search` (`pagefind.ts`, a same-origin dynamic import), on first open and after the list is on screen, so the index is not on the path to interactivity. A page the palette already lists is not repeated from the index. A failed load shows a visible note and `console.warn`.
- **Panels**: each page is listed once per panel (hub, then the tile, then the columns, then the strip; a repeat is dropped where it is less prominent, never across panels). A column shows descriptions only when every one of its links has one, so no column mixes tall rows with short ones. The lead is a full-width row with the section name as an eyebrow; the strip is a quiet footer line; the Resources tile names the newest published research brief, with no date.
- **Drawer**: Search entry, sections (the only row that scrolls) and a sticky Apply, which is not rendered on `/apply/` and `/contact/` (the same rule as the fixed bar).
- **`/search/` chips**: the first 50 results are fetched after the first page is on screen; the chips list the types found (two or more), a chip filters them, `?type=` keeps the choice, and the status line names the type. When there are more than 50 matches it says the filter covers the first 50.

The new specs live in `tests/e2e/wave7/wp-46/`, which the existing projects do not match (their patterns are `/<name>.spec.ts$` under `tests/e2e/`); the `e2e:wave7` job runs them.

Two fixes came out of the first full e2e run. The palette no longer closes its dialog before it navigates (a cross-document view transition aborted with "invalid state"; `pagehide` closes it, so a page restored from the history never shows it open). The results list ignores the pointer for 400 ms after "Show more", because the second click of a double click landed on a result that the first batch had moved under the pointer. The `e2e:a11y` timeouts on the same run (axe on `/program/`, the mega-menu panels) were runner load: every test took about 2.5 times its time on the demo run, and they passed on the next pipeline without a change to the panels.

Known limit: the type chips cover the first 50 matches of a search (the status line says so when there are more).
