## State

The service is code-complete and inert. Until the operator supplies OP-AZURE, OP-FD, OP-DV, OP-MAIL and OP-RETAIN (`docs/intake-runbook.md`) the forms stay `disabled` and `verify:release` fails closed on a release tag. That is the intended outcome. Without the operator variables the demo pipeline has no `intake:deploy`, `intake:dataverse` or `intake:verify` job and is green.

WP-60 had not landed on `origin/demo` when this was written: `docs/forms-contract.schema.json`, the ownership lane for WP-61 and the `include: local` of `infra/intake/ci.yml` were absent. The server code therefore runs against a committed fixture copy of the schema (`infra/intake/tests/fixtures/forms-contract.schema.json`, written from the contract's required matrix). `intake:test` sets `REQUIRE_REAL_CONTRACT=1` as soon as the real file exists, which turns a drift between the fixture and the real file into a failing test. The shape was agreed with main and is the one `contract.ts` reads: `{ "version": 2, "redirectAllowlist": [paths], "kinds": { "<kind>": { "thanks", "audience", "rateLimit": { "perHour": 5 }, "fields": { "<field>": { "rule", "type", "max"?, "enum"? } } } } }`. `redirectAllowlist` and `rateLimit` are optional on read (the allowlist then holds only the kinds' thanks paths, the limit defaults to 5), and the per-kind limit is passed to the rate store. If WP-60's JSON differs, `parseContract` in `infra/intake/src/logic/contract.ts` is the one place to adapt.

## Where this differs from #41 or the contracts, and why

Where they disagreed, the contracts won.

- `host.json` lives in `infra/intake/src/` and is packaged to the zip root. The brief named a root-level `host.json` outside the write set; the package step places it correctly, so no root file is needed.
- The Dataverse role also has Account Create (and a `we_accountkey` column and alternate key on Account), because the contract upserts an Account per business email domain. The contract text said read and write only.
- An extra `we_review` column marks an ambiguous contact match (more than one contact with the same email) for a person to resolve rather than guessing.
- A requested brief is treated as transactional mail and is not gated by suppression. Marketing mail (the nurture sequence, off) is gated. Every email still carries an unsubscribe link and the RFC 8058 headers.
- `intake:verify` is a separate manual job, not a step of `intake:deploy`, because it can only pass after the operator finishes OP-FD (DNS, origin).
- `POST /api/newsletter` is an alias of the intake route for the newsletter form, so `PUBLIC_WE_NEWSLETTER_API_URL` can point at it. The newsletter sends no acknowledgement email and has no thanks page.
- A form-encoded post with `Origin: null` is accepted (browsers send it from some cross-site form posts); JSON posts need an allowlisted Origin.
- A replayed `requestId` still consumes rate-limit quota (the limiter runs before the idempotency lookup), so a script cannot replay one request without limit.
- Body cap is 32 KiB, well above the largest legal form (4,000-character message plus the other fields).
- The Dataverse applier creates the owner team; the staff security role and team membership are left to the operator (runbook, OP-DV step 5).
- If the ACS status poll times out, the send is treated as accepted (the service has no way to distinguish a slow success from a failure, and a retry would risk a duplicate).
- Registry versions may be dotted (`"1.0"`), because the brief front matter uses `version: 1.0`.
- The renderer prints PDFs with the Playwright image's own Chromium (`findChromium`, `CHROME_BIN` override). No dependency was added to the root `package.json`.
- The Bicep binary is downloaded in CI at a pinned version with a sha256 check (v0.48.1), and the what-if gate is a Node script, so it is unit-tested on a deleting fixture.
- The delivery-failure alert queries Application Insights `AppTraces`, which is where the Function's log lines land.
- Brief versions are immutable: the publisher stores a sha256 in blob metadata and refuses to overwrite a published version with different bytes. The registry is uploaded last so a reader never sees an entry without its files.
- The nurture sequence is code and tests only, behind `NURTURE_ENABLED=false`.
- An unknown kind or an unknown field is rejected with 422 and a field error (main's note said 400; the assignment allowed 400 or 422). Malformed JSON stays 400. Nothing unknown is passed through to the store.

- `infra/intake/briefs/` is WP-63's. The renderer and `intake:render` are inert while it is empty.
- `.gitlab-ci.yml` needs, once, `include: - local: infra/intake/ci.yml` guarded by `rules: exists: [infra/intake/ci.yml]` (WP-60 is to add it), and the ownership lane for WP-61 (`check:ownership` currently reports "no assignment for WP-61" on this branch).
- `.gitignore`: the root file already ignores `dist/` and `node_modules/`. `infra/intake/render/out/` (the renderer's output, produced in CI and uploaded as an artifact) is not ignored; a one-line addition by main keeps a local render run from showing as untracked. `infra/intake/.gitignore` is outside the write set and was not added.

For the operator: OP-AZURE, OP-FD, OP-DV, OP-MAIL and OP-RETAIN, plus OP-COUNSEL (review of the notice, the unsubscribe flow and the nurture sequence) and OP-FLAGS (`flags.briefUpdates`, `NURTURE_ENABLED`, the site's `PUBLIC_WE_INTAKE_API_URL` and `PUBLIC_WE_NEWSLETTER_API_URL`). All are in `docs/intake-runbook.md`.

Known limits:

- The CI jobs that deploy and verify were validated as YAML and by reading, not run: they need Azure and cannot run without the operator's variables. `intake:test` and `intake:render` are the jobs that run on every branch.
- `intake:test` and `intake:render` were exercised in real CI on a throwaway probe branch (pipeline 65442 passed) because the root pipeline does not include `ci.yml` yet. That run showed the runner reaches `github.com` for the pinned Bicep binary and that the job user cannot write `/usr/local/bin`, so the binary now lives in `$CI_PROJECT_DIR/.tools`.
- The runbook's Entra federated-credential subject and role list describe what the Bicep and jobs need; they were not exercised against a real tenant.
